# SAFEZONE — REST API Endpoints

**Базовый префикс:** `/api/v1`

Статусы:
- `[ГОТОВО — логика]` — бизнес-логика существует, требуется REST-эндпоинт.
- `[ЧАСТИЧНО]` — часть логики существует, необходимы доработки.
- `[НЕ РЕАЛИЗОВАНО]` — функциональность отсутствует.
- `[ОТЛОЖЕНО]` — функциональность запланирована на будущее.

## 1. Аутентификация — `/auth`

| Метод и эндпоинт | Доступ | Статус и комментарий |
|---|---|---|
| `POST /auth/register` | GUEST | `[ЧАСТИЧНО]` Регистрация есть в `SafeZoneService.register()`. Нужно добавить REST-контроллер и DTO. Хеширование паролей необходимо перевести с SHA-256 на BCrypt или Argon2. |
| `POST /auth/login` | GUEST | `[ЧАСТИЧНО]` Проверка логина и пароля реализована в `SafeZoneService.login()`. Нет JWT и механизма выдачи токенов. |
| `POST /auth/refresh` | AUTH | `[НЕ РЕАЛИЗОВАНО]` Нет refresh-токенов и механизма их обновления. |
| `POST /auth/logout` | AUTH | `[НЕ РЕАЛИЗОВАНО]` Нет токен-сессий или механизма отзыва токенов. |
| `GET /auth/me` | AUTH | `[ЧАСТИЧНО]` Пользователя можно найти в БД, но нет авторизации через токен и определения текущего пользователя HTTP-запроса. |

`GUEST` — запрос без авторизации. `AUTH` — запрос с действительным токеном.

## 2. Профиль пользователя — `/users`

| Метод и эндпоинт | Доступ | Статус и комментарий |
|---|---|---|
| `GET /users/me` | AUTH | `[ЧАСТИЧНО]` Получение пользователя по ID реализовано, но нет определения текущего пользователя из токена. |
| `PATCH /users/me` | AUTH | `[НЕ РЕАЛИЗОВАНО]` Изменение профиля через сервис и репозиторий не предусмотрено. |
| `PATCH /users/me/password` | AUTH | `[ОТЛОЖЕНО]` Смена пароля пока не предусмотрена. Добавить позднее: проверка текущего пароля, валидация нового пароля и безопасное сохранение нового хеша. |

## 3. Управление пользователями — `/users`

| Метод и эндпоинт | Доступ | Статус и комментарий |
|---|---|---|
| `GET /users` | ADMIN | `[ГОТОВО — логика]` `SafeZoneService.getUsers()` и `UserRepository.findAll()` существуют. Нужны REST-контроллер и проверка роли ADMIN. |
| `GET /users/{userId}` | ADMIN | `[ГОТОВО — логика]` Есть `SafeZoneService.findUserById()`. Нужны REST-контроллер и проверка роли. |
| `PATCH /users/{userId}/status` | ADMIN | `[ЧАСТИЧНО]` Есть блокировка, разблокировка и логическое удаление через `blockUser()`, `unblockUser()` и `deleteUser()`. Нужно определить допустимые переходы статусов и реализовать эндпоинт. |
| `PATCH /users/{userId}/role` | ADMIN | `[НЕ РЕАЛИЗОВАНО]` Изменение роли отсутствует в сервисе и репозитории. В модели и БД роли `CLIENT` и `ADMIN` уже предусмотрены. |

При регистрации роль пользователя автоматически назначается как `CLIENT`. Пользователь не должен иметь возможность самостоятельно назначать себе `ADMIN`.

## 4. Склады — `/warehouses`

| Метод и эндпоинт | Доступ | Статус и комментарий |
|---|---|---|
| `GET /warehouses` | GUEST | `[ГОТОВО]` Получение списка реализовано в `SafeZoneService.getWarehouses()`. |
| `GET /warehouses/{warehouseId}` | GUEST | `[ГОТОВО]` В репозитории есть `findById()`, но в `SafeZoneService` нет соответствующего публичного метода. |
| `POST /warehouses` | ADMIN | `[НЕ РЕАЛИЗОВАНО]` Создание склада отсутствует в репозитории и сервисе. |
| `PATCH /warehouses/{warehouseId}` | ADMIN | `[НЕ РЕАЛИЗОВАНО]` Обновление склада отсутствует. |
| `DELETE /warehouses/{warehouseId}` | ADMIN | `[НЕ РЕАЛИЗОВАНО]` Удаление склада отсутствует. Нужно учесть связанные ячейки и аренды. |

## 5. Ячейки хранения — `/cells`

| Метод и эндпоинт | Доступ | Статус и комментарий |
|---|---|---|
| `GET /cells` | GUEST | `[ГОТОВО — логика]` Список ячеек реализован в `SafeZoneService.getCells()`. |
| `GET /cells/available` | GUEST | `[ЧАСТИЧНО]` Есть получение доступных ячеек. Проверку пересечения интервалов аренды нужно согласовать с параметрами запроса, если доступность требуется на конкретный период. |
| `GET /cells/{cellId}` | GUEST | `[ГОТОВО — логика]` Есть `SafeZoneService.findCellById()`. |
| `GET /warehouses/{warehouseId}/cells` | GUEST | `[ЧАСТИЧНО]` Получение всех ячеек есть, но отдельной выборки ячеек конкретного склада в репозитории нет. |
| `POST /warehouses/{warehouseId}/cells` | ADMIN | `[НЕ РЕАЛИЗОВАНО]` Создание ячейки отсутствует. |
| `PATCH /cells/{cellId}` | ADMIN | `[НЕ РЕАЛИЗОВАНО]` Изменение параметров ячейки отсутствует. |
| `PATCH /cells/{cellId}/status` | ADMIN | `[НЕ РЕАЛИЗОВАНО]` Перечисление статусов `AVAILABLE`, `RENTED`, `UNAVAILABLE` существует, но изменение статуса через сервис и репозиторий не реализовано. |
| `DELETE /cells/{cellId}` | ADMIN | `[НЕ РЕАЛИЗОВАНО]` Удаление ячейки отсутствует. Нужно учитывать связанные аренды. |

**Примечание по доступности:** в сервисе есть проверка занятости ячейки на временном интервале. Однако перегрузка `getAvailableCells(startDateTime, endDateTime)` сейчас возвращает список ячеек со статусом `AVAILABLE`, не отфильтровывая их по пересечению аренды. Эту часть нужно доработать, прежде чем использовать её для поиска свободных ячеек на период.

## 6. Аренды — `/rentals`

| Метод и эндпоинт | Доступ | Статус и комментарий |
|---|---|---|
| `POST /rentals` | CLIENT | `[ГОТОВО — логика]` Создание аренды реализовано через `rentSpecificCell()` и `rentCellBySize()`. Нужно определить DTO запроса и связать операцию с текущим пользователем из токена. |
| `GET /rentals/me` | CLIENT | `[ГОТОВО — логика]` Есть `SafeZoneService.getUserRentals(userId)`. Требуется авторизация и получение ID из токена. |
| `GET /rentals/{rentalId}` | CLIENT / ADMIN | `[ЧАСТИЧНО]` Поиск аренды реализован. Проверка владельца аренды для CLIENT и проверка роли ADMIN должны быть добавлены на уровне API. |
| `PATCH /rentals/{rentalId}/cancel` | CLIENT | `[ЧАСТИЧНО]` Отмена аренды реализована в `cancelRental()`. Необходимо проверить, что CLIENT отменяет только собственную аренду. |
| `GET /rentals` | ADMIN | `[ГОТОВО — логика]` Получение всех аренд реализовано через `SafeZoneService.getRentals()`. Требуется ограничение доступа по роли ADMIN. |
| `PATCH /rentals/{rentalId}/status` | ADMIN | `[ЧАСТИЧНО]` Репозиторий умеет изменять статус аренды, но административного сценария управления статусами с проверкой допустимых переходов нет. Сейчас в сервисе предусмотрена отмена активной аренды. |

При создании аренды сервис проверяет доступность ячейки и ограничивает продолжительность аренды диапазоном от 1 до 24 часов. В API необходимо валидировать даты, продолжительность и существование пользователя и ячейки.

| `GET /actuator/health/readiness` | INTERNAL | `[НЕ РЕАЛИЗОВАНО]` Нет проверки готовности приложения и подключения к БД через Actuator. |

## 8. Общие задачи перед запуском API

- Добавить Spring Boot Web, Spring Security и необходимые зависимости.
- Создать REST-контроллеры, DTO запросов и ответов, валидацию и единый формат ошибок.
- Реализовать JWT-аутентификацию и разграничение ролей `CLIENT` и `ADMIN`.
- Исключить выдачу `passwordHash` в API-ответах пользователя.
- Перевести хеширование паролей с SHA-256 на BCrypt или Argon2.
- Реализовать недостающие методы сервисов и репозиториев для складов и ячеек.
- Добавить проверку владельца аренды и корректные переходы её статусов.
- Добавить пагинацию и фильтрацию для списков пользователей, ячеек и аренд.
- Добавить обработку ошибок `400`, `401`, `403`, `404` и `409`.
- Добавить Dockerfile и Docker Compose, если развёртывание в контейнерах входит в требования проекта.
