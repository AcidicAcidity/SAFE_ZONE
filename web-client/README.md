# SafeZone Web

Самостоятельный React-клиент к существующему Spring Boot API. Оформление и расположение основных элементов следуют JavaFX-клиенту: светлый фон, белая шапка с аккаунтом, главное меню из карточек, табличные разделы и отдельное меню администратора. На небольших экранах карточки располагаются в одну колонку, таблицы прокручиваются внутри панели.

JavaFX и консольный клиент остаются самостоятельными. API использует конфигурацию Docker и поддерживает операции записи веб-клиента.

## Запуск в Docker

Все команды в этом разделе выполняются **из корня репозитория**.

Используйте настроенный корневой `.env` для существующего backend. Если его ещё нет, скопируйте `.env.example` в `.env` и задайте свои `DB_NAME`, `DB_USER`, `DB_PASSWORD` и `JWT_SECRET` (не менее 32 символов). Не заменяйте уже существующий `.env`.

```sh
docker compose -f docker-compose.yml -f web-client/docker-compose.yml up -d --build
```

Открыть: **http://localhost:3000**. Порт можно изменить через `WEB_PORT=3001` перед командой. Корневой Compose остаётся первым файлом: относительные пути сборки и volume вычисляются от него. Используйте одинаковый набор `-f` при последующих командах.

Пересобрать только web, не перезапуская существующий API и БД:

```sh
docker compose -f docker-compose.yml -f web-client/docker-compose.yml up -d --build --no-deps web
```

Посмотреть логи и остановить только веб-клиент:

```sh
docker compose -f docker-compose.yml -f web-client/docker-compose.yml logs -f web
docker compose -f docker-compose.yml -f web-client/docker-compose.yml stop web
```

Node используется при сборке. Готовый контейнер содержит Nginx и статические файлы. Nginx раздаёт приложение, поддерживает прямое открытие вложенных страниц и проксирует `/api/` в `http://api:8080` в общей Compose-сети. Браузеру не нужно знать Docker-имена, CORS не требуется. `/healthz` проверяет сам веб-сервер; готовность API проверяется отдельно.

Compose запускает PostgreSQL, затем API и ждёт его успешного healthcheck, после чего запускает web. Настройки БД и начального администратора API получает из окружения Docker; корневой `.env` используется Compose. Существующие данные volume сохраняются.

## Локальная разработка

Node.js 22.12+ (для Docker используется Node 24).

```sh
cd web-client
npm ci
cp .env.example .env.local
npm run dev
```

Открыть http://localhost:3000. API должен работать отдельно, по умолчанию на http://127.0.0.1:8080. Другой адрес задаётся через `API_PROXY_TARGET` в `.env.local`; запросы браузера по-прежнему идут на `/api/` текущего сайта. Не помещайте пароли БД и `JWT_SECRET` в `VITE_*`: такие значения попадают в браузерную сборку.

## Реализованные возможности

- Регистрация, вход, получение текущего пользователя, выход из аккаунта.
- JWT в `sessionStorage` текущей вкладки, восстановление после обновления, выход по сроку действия токена или защищённому ответу 401. Пароли не сохраняются. Серверного refresh/logout endpoint в текущем API нет.
- Склады и ячейки: реальные данные API, поиск по таблице, сортировка, состояния загрузки, пустого списка и ошибок, ручное обновление.
- Подбор и оформление аренды: конкретная свободная ячейка либо размер, срок 1–24 часа, предварительное отображение выбора.
- Собственные аренды клиента и отмена действующей брони с подтверждением. После отмены списки повторно загружаются с сервера.
- Администратор: список всех броней и их отмена, список пользователей с блокировкой, разблокировкой и удалением аккаунта, статистика количества аренд каждой ячейки. Статистика считается из доступных списков ячеек и всех аренд, включая отменённые и завершённые; ячейки без аренд также отображаются.
- Администратор может просматривать свои аренды через фильтрацию разрешённого ему общего списка. Административные страницы защищены маршрутизацией; проверка полномочий остаётся на сервере.

В рабочем приложении нет демонстрационных данных. Тестовые ответы используются только в `tests/`.

## Совместимость с API

Текущий backend поддерживает регистрацию, вход, аренду и изменение статусов. При запуске через Compose операции записи включены автоматически. Флаги позволяют явно отключать их при подключении к старому API:

```dotenv
VITE_ENABLE_RENTAL_CREATION=true
VITE_ENABLE_USER_STATUS_UPDATES=true
VITE_ENABLE_RENTAL_STATUS_UPDATES=true
```

Для локальной разработки скопируйте `.env.example` в `.env.local`. Для Docker флаги можно переопределить в корневом `.env` либо окружении команды Compose, затем пересобрать `web`. Флаги не заменяют проверку прав сервером. Экспорт полной базы в XLSX пока недоступен: HTTP endpoint отсутствует.

Адаптер `src/net/client.ts` сохраняет совместимость с историческими именами `Role`, `addr`, `startRent` и `endRent`. Список всех аренд запрашивается по стандартному маршруту; для прежнего API сохранён fallback на повторяющийся маршрут после 404/405. Запрос текущих свободных ячеек передаёт обе даты — такой вызов поддерживают обе версии контроллера. Окончательная проверка всего выбранного срока выполняется сервером при создании аренды.

Даты передаются в формате API `LocalDateTime` без часового пояса. Статусы и просроченность аренды отображаются по ответам сервера.

## Проверки

```sh
cd web-client
npm run build
npm test
npx playwright install chromium
npm run test:e2e
```

Если Chrome уже установлен, можно использовать его без скачивания Chromium:

```sh
PLAYWRIGHT_CHANNEL=chrome npm run test:e2e
```

Unit-тесты проверяют совместимость DTO, маршруты, JWT, ошибки и подсчёт статистики. Браузерные тесты работают с перехватом HTTP-запросов: клиентские и административные сценарии, регистрация, отмена брони, восстановление сессии, 401, ошибка сервера и мобильная ширина. Скриншоты сохраняются в игнорируемом `test-results/`. Это проверка клиента по контрактам API, а не замена проверки на живой БД.

## Структура

```text
src/
  model/       Типы данных, статусы, подсчёт статистики
  net/         HTTP-клиент, адаптеры DTO, авторизация, запросы и флаги возможностей
  ui/          Страницы, auth/, общие components/
  util/        Форматирование дат и сообщений
  styles/      Стили и адаптивная вёрстка
tests/         Браузерные сценарии
```
